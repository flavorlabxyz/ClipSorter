# V1.6: organization, reset, and experimental matching

This upgrades the existing FastAPI/plain JavaScript/SQLite application. The official-SDK BRAW bridge is unchanged. The user reports that V1.5 runs on Fedora and processes their BRAW footage; this release has not independently repeated that workstation acceptance. No source footage or live user library was available during development.

## Install and upgrade on Fedora

Stop the old server first. Keep its code/virtual environment available for rollback. Copy the **application data directory**, not the source-media directory, to a backup location while the server is stopped. This also preserves disposable images and models for a complete recovery.

```bash
sudo dnf install python3 python3-pip gcc-c++ ffmpeg-free nodejs
cd /path/to/recipe-clip-sorter
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[test]'
recipe-sorter --data-dir "$HOME/.local/share/recipe-clip-sorter" diagnostics
recipe-sorter --data-dir "$HOME/.local/share/recipe-clip-sorter" serve
```

Use your actual existing data path if different. The default remains `$XDG_DATA_HOME/recipe-clip-sorter`, or `~/.local/share/recipe-clip-sorter`. Generated output must remain separate from source media. Open http://127.0.0.1:8765. Existing BRAW bridge/SDK environment variables and setup from README remain applicable. Preserve them in the shell used to launch V1.6.

For CLIP, retain the installed local model and AI dependencies. On a fresh installation only:

```bash
python -m pip install -e '.[ai]'
recipe-sorter --data-dir "$HOME/.local/share/recipe-clip-sorter" prepare-model
```

`prepare-model` explicitly downloads weights; inference remains local and offline. No CLIP or BRAW fallback is hidden behind the baseline. Demo: `recipe-sorter --data-dir /tmp/recipe-sorter-demo serve --demo` uses its own demo subtree.

### Migration and rollback

Opening a V1.5 database automatically applies schema 3 and first creates `library.pre-v1.6.sqlite3` using SQLite's consistent backup API. A V1 database first goes through the existing schema-2 migration. Original groups, manual overrides, correction/proposal history and valid cached analysis remain. Newer schema versions are refused. Keep one application process per library and stop CLI/server work before upgrading.

Schema 3 adds:

- A sorting generation and organization revision, plus generation IDs on groups, automatic runs, moves, recommendation runs and decisions.
- Clip sorting state: `unsorted`, `grouped`, or `uncertain`, separate from processing status and manual overrides.
- Persistent reset snapshots/backup paths and per-run analysis summaries.
- Independent benchmark labels with source fingerprint, recipe, filming session, stage and optional split.

Historical rows are retained; retired groups are tombstones, preserving references. The reset revision protects against confirmation in one tab silently overwriting changes from another. Old undo and recommendation decisions cannot become active in a new generation, even after restoring old group IDs.

**Code rollback:** do not open schema 3 with V1/V1.5. Stop the server, copy the application directory into a new recovery directory, replace that copy's `library.sqlite3` with `library.pre-v1.6.sqlite3`, and remove only the recovery copy's `library.sqlite3-wal` / `library.sqlite3-shm` if present. Run the old application with that new `--data-dir`. This returns to the migration-time organization; later work is not merged. Never replace a database while it is open. Never put a recovery database in a source directory.

## Short walkthrough

1. **Move directly between recipes.** Grab a card's **Move** handle and drop on another sidebar group or visible workspace group. Preview, checkboxes and sample selectors remain separate controls. Drag a selected card to move the whole selection; drag an unselected card to move only it. The selection bar and drag ghost show hidden selected clips. Pause near a scroll area's edge to reach further destinations. Checkboxes plus the **Move** control provide a keyboard-accessible alternative.
2. **Undo.** Use Undo move or Ctrl+Z. Manual moves commit atomically and persist across restart/reanalysis. Dropping into the effective current group does nothing and adds no undo entry. To deliberately confirm an automatic proposal as a trusted human example, open the clip and use **Save assignment**; confirmation is distinct from a same-group drop.
3. **Clean empty groups.** Remove empty groups… reports the full-library count and requires confirmation. Filters cannot make a populated group appear empty to this operation. Empty manual groups remain valid targets until you explicitly delete/clean them. Reanalysis automatically retires obsolete empty automatic groups.
4. **Reset sorting…** reports the actual affected clip/group counts and requires confirmation. It clears active assignments and recipe groups, leaving all clips truly unassigned, not manually locked to Uncertain. Original files, scans, metadata, thumbnails, proxies, embeddings, models, labels and history stay intact. No analysis starts automatically. Processing errors remain visible; the status filter distinguishes Unsorted from Analyzed but uncertain.
5. **Restore previous sorting…** restores the persisted pre-reset virtual organization, including after restarting and while sources are offline. It refuses if subsequent organization, scanning changes or recommendation work would be overwritten. It retains independently updated benchmark truth. Historical undo/rejections remain inactive; new recommendations use a fresh generation.
6. **Try improved analysis.** Analyze clips → Local CLIP → **Guarded average-link (experimental)**. Uniform five-frame sampling remains the default; bounded adaptive/diverse modes are optional. The summary shows processed/failed/protected/grouped/uncertain counts and reasons. Clip details expose neighboring clips and the reason a proposal was withheld.
7. **Find matches.** Manually confirm diverse recipe stages, then choose **Balanced diverse prototypes (experimental)** in Find matches. Review supporting frame pairs, coverage and competing evidence. Accept/reject/skip are saved; ambiguous candidates remain reviewable. Scores are similarities, never probabilities. The V1.5 example bank remains available for comparison.

### Reset safety and recovery limits

Reset and restore take an SQLite write transaction, validate the displayed generation/revision, create a timestamped consistent backup under `backups/`, then change virtual organization atomically. Backup failure aborts before mutations. The application refuses these operations while a scan, analysis, preview or recommendation job runs. Proposal/recommendation commits also validate the captured generation. A stale browser cannot undo or accept an old-generation action.

Restore only permits the exact post-reset organization state; it does not merge new work. If it reports a conflict, preserve the current library and recover a timestamped backup into a **separate application directory**, as described above, using V1.6 for schema-3 backups. Inspect both libraries before deciding which organization to keep. This is deliberately conservative; even new recommendation work prevents automatic restore. Cache-only reads and independent truth-label changes do not block restore.

## API changes

`GET /api/organization` returns full counts, a generation/revision token and restore availability. `POST /api/organization/reset`, `/cleanup`, and `/restore/{reset_id}` require `{generation, revision, confirmed:true}`. They use the same local-only host/origin/header checks as existing mutations. All tokens are validated in the write transaction.

`POST /api/assign` returns `moved` and nullable `move_id`; optional `confirm:true` explicitly confirms examples. Analysis accepts `method:complete|guarded` and `sampling:uniform|adaptive|diverse`; recommendations accept `method:bank|prototypes`. `POST /api/clips/{id}/label` stores independent truth (`recipe`, `session`, `stage`, `split`). A nonempty recipe label is required. `GET /api/library` includes `sorting` and the latest current-generation `analysis_summary`.

## Tests and workstation acceptance

```bash
python -m unittest discover -s tests -v
node tests/frontend.test.cjs
python -m compileall -q recipe_sorter scripts tests
node --check recipe_sorter/frontend/app.js
node --check recipe_sorter/frontend/sorting.js
python -m pip install -e '.[browser]'
python -m playwright install chromium
python scripts/browser_smoke.py
python scripts/browser_acceptance.py
```

The new rendered-browser script builds an isolated **non-demo** FFmpeg library with read-only sources, real analysis, manual groups, empty groups and rejected suggestions. It checks direct/bulk/filtered dragging, scrolling, no-op, undo/restart, full-library cleanup, reset/cancel/backup failure/stale confirmation, stale decisions, restore, new-generation suggestions, mobile overflow and original hashes. Logs/screenshots are under `.test-data/browser-v16-*`. It does not open your data. Set `RCS_BROWSER_EXECUTABLE=/usr/bin/chromium` if using a Fedora system Chromium instead of Playwright's binary. Native drag behavior must also be reviewed in your preferred browser, particularly Firefox; this script targets Chromium.

[VALIDATION.md](VALIDATION.md) distinguishes executed tests from blocked browser/Fedora/SDK checks. [V1_6_EVALUATION.md](V1_6_EVALUATION.md) contains the audit, actual synthetic results, and local labeled-footage benchmark commands.
